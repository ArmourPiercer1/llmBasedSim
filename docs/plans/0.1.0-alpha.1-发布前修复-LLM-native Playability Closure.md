可以。这个阶段最合适的定位不是 `alpha.2`，也不是 P11，而是：

> **0.1.0-alpha.1 Pre-release Remediation — LLM-native Playability Closure**
>
> 目的：修复最小游戏实测暴露出的一个 release-blocking capability gap，使 `0.1.0-alpha.1` 真正具备“真实 LLM 驱动 + 玩家自然语言输入 → 权威游戏动作”的最小闭环。**不增加版本号，不扩展原定 alpha.1 的总体产品边界。**

现有基础其实已经很充分：真实 OpenAI-compatible HTTP backend、deployment、NPC `LLMPolicy`、结构化 JSON 解析与 repair、以及 production `assemble_project(deployment=..., inference_backend=...)` 都已经存在。   现有实玩脚本甚至已经能把真实 backend 接进 production assembly，只是玩家侧仍靠固定命令映射，并非自然语言。

# 0.1.0-alpha.1 发布前修复计划：LLM-native Playability Closure

## 1. 修复目标

本轮结束时，必须能够完成下面这条真实 production path：

```text
GameProject
+ DeploymentProfile
+ real InferenceBackend

玩家自然语言
      ↓
Player Intent Interpretation
      ↓
structured action selection
      ↓
ActionProposal
      ↓
ActionExecutor
      ↓
custom solver / game logic
      ↓
ProposedEffect(s)
      ↓
Authority
      ↓
Transaction
      ↓
Reducer
      ↓
authoritative WorldState
```

同时 NPC 保持：

```text
ActorDecisionContext
      ↓
LLMPolicy
      ↓
real InferenceBackend
      ↓
ActionProposal
      ↓
同一 authoritative pipeline
```

这里最重要的版本语义是：

> **LLM 负责理解意图和提出动作，不负责决定 authoritative outcome。**

因此这仍然完全符合 K2/K3/K5，而不是对架构进行新一轮扩建。

---

## 2. Scope 冻结

这轮允许修改的范围应严格限制在：

| 范围                         | 本轮处理            |
| -------------------------- | --------------- |
| 真实 LLM production wiring   | 是，补正式入口和验收      |
| 玩家自然语言解析                   | 是               |
| action grounding           | 是，最小实现          |
| 复用现有 LLM structured parser | 是               |
| live-LLM E2E / smoke       | 是               |
| NPC LLM production path 修补 | 仅发现直接 blocker 时 |
| Kernel / Authority 重构      | 否               |
| Scheduler / long action    | 否               |
| P11 Dev Control Plane      | 否               |
| 通用 tool-calling framework  | 否               |
| P5 Action DSL 大改           | 否               |
| 完整 dialogue framework      | 否               |
| WebUI                      | 否               |
| DSH                        | 否               |
| multi-agent orchestration  | 否               |
| 新版本号                       | **否**           |

尤其不要因为自然语言解析需要动作描述，就顺手重构整个 ActionSpec authoring。当前 runtime 项目 action 绑定甚至把参数表设为 `{}`，说明完整参数 schema 的 production wiring 还没完成。 这一缺口可以后续正式处理，本轮采用薄 grounding seam。

# 3. R1 — 建立 Player Intent Interpreter

这是本轮唯一真正新增的核心能力。

建议建立独立 runtime/LLM seam，例如概念上：

```python
PlayerIntentInterpreter.interpret(
    text,
    context,
    grounding,
) -> PlayerIntentResult
```

它不应直接修改 Engine，也不负责运行 action。

建议返回中间结果：

```python
PlayerIntentResult(
    action_id: str | None,
    arguments: dict,
    intent: str | None,
    confidence: float | None,
    raw_output_ref: str | None,
    diagnostics: tuple[...],
)
```

然后 host 再调用：

```python
engine.submit_action(
    actor_id,
    result.action_id,
    result.arguments,
    intent=result.intent,
)
```

这样可以保持：

```text
Natural Language Adapter ≠ Engine
```

### 实现要求

优先复用现有：

```text
InferenceBackend
InferenceRequest
LLMActionProposal
parse_llm_response()
repair_instruction()
```

当前 NPC `LLMPolicy` 已经完成“调用 → parse → 一次 repair → structured action”的大部分机制。

不要复制一整套第二 parser。

可以抽取很薄的 shared helper；如果抽取会明显扩大改动，也允许 alpha.1 暂时复用现有 public functions 并保留少量 orchestration duplication。

### failure semantics

至少明确：

```text
无法解析
→ 最多一次 repair
→ 仍失败
→ PlayerIntentResult(action_id=None)
→ 不调用 submit_action
→ 世界不变
```

模型 hallucinate 未注册 action：

```text
Interpreter 可以返回
→ Engine.submit_action()
→ unknown_action
→ 世界不变
```

不要在 interpreter 里复制 Engine 的 authority/registry 判定逻辑。

# 4. R2 — 建立最小 Action Grounding

自然语言输入真正需要的是：

> 模型不仅知道有哪些 action，还知道这些 action“是什么意思、需要什么参数，以及当前有哪些合法实体可引用”。

当前 context 已经有 `candidate_actions`，但它本质上只是 action ID 集合。

本轮新增一个轻量 grounding representation，例如：

```text
ActionGrounding
- action_id
- human-readable description
- argument hints
```

其来源可以是：

```text
GameProject / extension metadata
```

而不必成为新的 Kernel contract。

建议支持这样的抽象数据：

```yaml
actions:
  use:
    description: 对一个可见或持有的实体执行使用行为
    arguments:
      target: 可交互实体 ID
      item: 可选的 inventory item ID
```

这里只是示意 shape，不要求实际使用 YAML。

### Grounding prompt 至少提供

```text
candidate actions
action descriptions
argument hints
player identity
visible/local entities
relevant inventory/entities
current authoritative state subset
user natural-language input
```

其中“模型能看到什么”仍必须服从已有 context/capability 边界。

不要为了方便直接把整个 WorldState dump 给模型。

---

# 5. R3 — 正式接通真实 LLM 配置

这部分原则上是 glue，而不是新 subsystem。

现有 `DeploymentProfile` 已支持：

```text
models
inference_profiles
base_url
api_key_env
temperature
timeout
fallbacks
```

并且已有 deployment file loader。

本轮要求把玩家 intent interpreter 也放入 capability/deployment 体系。

例如增加逻辑 capability：

```text
player_intent
```

从而允许：

```text
npc_policy → model A
player_intent → model B
```

或：

```text
npc_policy → model A
player_intent → same model A
```

### 不应做

不要：

```text
在 GameProject 中保存 API key
硬编码 OpenAI/DeepSeek
给 PlayerIntentInterpreter 自己写 requests/httpx
引入另一个 deployment 格式
```

必须继续复用 `InferenceBackend`。

# 6. R4 — 修正 alpha runner / playable runner

当前 `v2_alpha_run.py` 面向结构化：

```text
--action ACTION_ID:ENTITY_ID
```

而现有 `v2_runtime_play.py` 玩家命令依赖预定义短词映射。

本轮至少提供一个 production-only 自然语言入口，例如：

```text
> 我想……
```

内部：

```text
input()
→ PlayerIntentInterpreter
→ 显示解析结果
→ Engine.submit_action()
→ 显示 authoritative result
```

建议保留一个 debug 输出面：

```text
[input]
<原始文本>

[interpreted]
action_id=...
arguments=...
intent=...

[result]
ok=...
revision=...
diagnostics=...
```

这样 alpha 阶段非常利于人工审查 LLM grounding 问题。

### Fake 模式仍必须保留

正式 runner 应支持两条路径：

```text
--fake
```

用于确定性 CI；

以及：

```text
real backend
```

用于 release 前人工 smoke。

真实 API 不应成为普通单元测试的硬依赖。

# 7. R5 — 对话只做最小闭环，不建 Dialogue Framework

如果最小游戏需要角色语言输出，本轮可以支持，但必须保持最小。

推荐优先使用：

```text
talk action
arguments:
  target
  utterance
```

即：

```text
LLM
→ ActionProposal(
    action_id="talk",
    arguments={"target": ..., "utterance": "..."}
)
```

而不是增加第二条：

```text
LLM → freeform narration side channel
```

因为前一种形式以后能够自然进入：

```text
events
perception
memory
trace
```

本轮不要求把这些后续系统全部补完。

如果最小游戏不需要正式 dialogue semantics，则这项可以 CUT，不阻塞发布。

---

# 8. R6 — 测试矩阵

这一轮最重要的不是增加大量测试数量，而是覆盖跨层闭环。

建议至少包含一组 deterministic FakeInferenceBackend E2E 和一组人工 real-LLM smoke：

| Case                      | 必须结果                               |
| ------------------------- | ---------------------------------- |
| 普通自然语言 → 合法 action        | 成功提交                               |
| 自然语言 → 带 entity 参数 action | entity grounding 正确                |
| 自然语言 → 多参数 action         | arguments 正确                       |
| 模型返回坏 JSON                | repair 后成功或显式 no-op                |
| 连续两次坏输出                   | 世界不变                               |
| hallucinated action_id    | Engine 显式拒绝                        |
| hallucinated entity id    | executor/validation 显式拒绝           |
| 用户表达无法映射到动作               | no-op / explicit failure           |
| Fake backend 同输入双跑        | structured result + final world 一致 |
| real HTTP backend         | 至少完成一次真实自然语言→commit                |

特别要测试：

```text
LLM 成功解释 ≠ action 必须成功
```

例如模型正确解析某个动作，但 deterministic game rule 拒绝：

```text
natural language
→ 正确 ActionProposal
→ executor failure
→ 世界不变
```

这证明“LLM interpreter”和“world authority”确实分离。

# 9. 与上一轮 release blockers 的关系

本轮虽然定位为“LLM playability 修复”，但发布前仍应与之前发现的两个 P0 一起闭合：

```text
A. ActionExecutor 不得拿 raw mutable authoritative WorldState
B. runner 遇到 assembly ERROR 必须 non-zero / fail-closed
```

它们不是 LLM 功能的一部分，但都是同一个 `0.1.0-alpha.1` release gate。

因此建议最终发布门禁不是：

```text
LLM test passed
```

而是：

```text
Pre-release remediation passed
=
K2 direct-write closure
+ fail-closed runner
+ real LLM wiring
+ natural-language player intent
+ deterministic fake E2E
+ live-LLM smoke
```

这样仍然是一轮 **alpha.1 发布前修复**，不是新版本开发。

# Release Gate

这一轮完成后，我建议把 `0.1.0-alpha.1` 的新增 release gate 写成一句非常明确的话：

> **A user can provide free-form natural language to a production-assembled GameProject using a real configured LLM backend; the LLM grounds that intent into a structured game action, while the authoritative outcome remains exclusively determined and committed through the engine's existing executor/authority/transaction/reducer pipeline.**

只要这条成立，再加上前面已经要求的 K2 和 runner fail-closed 修复，**就不需要继续扩大 alpha.1**。此后遇到 action schema 通用化、tool calling、复杂 dialogue、memory、P11 等问题，都应该进入后续版本。
